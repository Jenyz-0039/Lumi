# 模块整合与风险控制方案

> 目标：以后将队友完成的模块三、模块七和模块十一安全接入当前网站。  
> 优先级：保护模块一、二、四、六、九、十；最小修改、可审查、可独立回退。

## 1. 推荐总体策略

采用“独立交付文件夹 + 主项目集成分支”的两阶段方式：

1. 队友在自己的环境按模块分别开发并交付完整文件夹。
2. 主项目先把交付包放到临时审查位置，不立即覆盖 `src/` 或 `public/`。
3. 审查源码、依赖、路径、许可证、资源体积和预览结果。
4. Git 主仓库恢复并建立基线后，为每个模块单独创建集成分支。
5. 将新文件复制到新文件名/新素材目录，只在集中入口做极少量切换。
6. 每个模块单独测试、单独提交；三个模块不合并成一个巨大提交。

队友的独立交付包便于跨电脑和跨 AI 工具协作；主项目的 Git 分支用于可追溯审查、对比和回退。两者不是互斥选项。

## 2. 队友必须交付的内容

每个模块独立交付：

- 正式 JS 模块文件。
- 模块专属 CSS 文件。
- 模块专属图片、视频、3D 模型、poster、decoder/worker/WASM 等全部运行资源。
- 独立预览页及运行说明。
- `README.md`：功能、交互、响应式、兼容性、已知问题。
- `INTEGRATION.md`：导出名、期望 ID/type、CSS 引入、初始化和 cleanup 接口。
- `DEPENDENCIES.md`：所有第三方依赖的精确版本、来源、许可证、体积和接入方式；无依赖也要明确写“无”。
- 素材来源/授权说明和第三方许可证。
- 文件清单，建议附 SHA-256。
- 桌面和手机截图；3D/复杂动画建议附短录屏。
- 测试清单：浏览器、视口、鼠标/触摸/键盘、reduced-motion、控制台错误、性能观察。

不得只交付构建后的单个压缩 JS，也不得只交付设计图或在线链接而缺少可审查源码和本地素材。

## 3. 接收和放置位置

### 审查阶段

不要把来件直接覆盖到正式路径。建议先放在主项目外部的安全临时目录，或在获得用户确认后放入项目中的：

```text
incoming-modules/
├─ module-03-character-3d/
├─ module-07-.../
└─ module-11-ending/
```

如果放入项目，先确认 Git 已恢复，并决定 `incoming-modules/` 是短期跟踪、Git LFS 跟踪还是明确忽略；不要让大模型和视频意外进入错误提交。

### 正式接入路径

```text
src/sections/Character3DSection.js
src/sections/Character3DSection.css
public/assets/module-03-character-3d/**

src/sections/ActionsSectionV2.js
src/sections/ActionsSectionV2.css
public/assets/module-07-*/**

src/sections/EndingSectionV2.js
src/sections/EndingSectionV2.css
public/assets/module-11-ending/**
```

新文件名与旧文件并存。不要删除 `CharacterSection.js`、`ActionsSection.js`、`EndingSection.js`，也不要覆盖现有素材。这使入口切回旧 renderer 即可回退。

## 4. 如何让整合者识别模块

收到交付后，向整合者明确提供：

1. 三个交付文件夹的绝对路径。
2. 每个模块对应序号、ID 和 type。
3. 哪个文件是正式入口，渲染/初始化/清理导出分别叫什么。
4. 哪些依赖已经由你批准，哪些仍待决定。
5. 设计稿、验收截图和必须保持的交互说明。
6. 模型/视频等大文件是否完整，是否有 Git LFS 或下载步骤。

整合者应先只读审查并给出计划，再执行复制和入口切换。任何交付包若修改了现有模块或全局配置，应先隔离差异，不能整包覆盖。

## 5. 模块三的最小修改接入

保持 `sections.js` 中模块三的以下字段不变：

```js
{ id: 'character', index: '03', type: 'character', ... }
```

接入时只需要：

1. 新增 `Character3DSection.js/.css` 和专属素材目录。
2. 在 `index.html` 新增该模块 CSS 的 `<link>`。
3. 在 `main.js` 把 `renderCharacter` 的 import/renderer 指向 `renderCharacter3D`。
4. 在页面渲染后调用 `initCharacter3D()`，保存其 cleanup 引用（如主项目随后引入统一 lifecycle）。
5. 删除或禁用只服务旧模块三的 `data-character-action` 公共监听，但仅在确认新模块不使用它后进行；不要动其他模块监听。

不改变模块 ID、数组顺序和总模块数，因此侧边导航、进度 `03 / 11` 和 IntersectionObserver 自动继续工作。

## 6. 模块七和最后模块的最小修改接入

### 模块七

- 默认保留 `id: actions` 和序号 `07`。
- 新增 V2 文件和素材目录。
- 在 `main.js` 切换 `actions` renderer，并调用它自己的 init。
- 设计语义确定后再修改这一项的 label/title/description；只有确有必要才改变 type，避免扩大修改范围。

### 模块十一

- 保留 `id: ending`、序号 `11` 和 type `ending`。
- 新增 V2 文件和素材目录，在 `main.js` 切换 renderer。
- 如需返回顶部，继续输出 `data-scroll-target="opening"`，让现有公共逻辑处理平滑滚动。
- 不自行重写导航、页码或全站结束流程。

## 7. 冲突预防

### CSS

- 每个模块一个唯一根类和唯一 BEM 风格前缀。
- 禁止全局标签选择器、`:root` 修改和未命名通用类。
- 模块内部 `isolation: isolate`，控制局部 z-index；fixed 元素、body class 和全局 cursor 必须单独审查。
- 新 CSS 以独立 `<link>` 引入，便于逐个禁用和定位。
- 接入前搜索类名、keyframes 名和 CSS 变量冲突。

### JavaScript

- 所有 DOM 查询以模块根为起点。
- 初始化幂等，所有全局监听、observer、timer、rAF 和 WebGL 资源可清理。
- 不覆盖 `window.onload`、`window.onscroll`、全局变量或原生 prototype。
- 不调用其他模块内部函数，不读取其他模块 DOM。
- 初始化失败用模块内错误边界/降级 UI 吸收，不能阻断 `main.js` 后续代码。

### 鼠标与触控

- 使用 Pointer Events，事件只在模块内生效。
- 不拦截全站滚动，不长期修改 body overflow/touch-action/cursor。
- 模块十已有局部自定义鼠标与拖拽逻辑，新模块的指针层和 z-index 不得覆盖模块十。
- 3D canvas 的拖拽旋转必须允许纵向页面滚动，并为 coarse pointer 提供合理降级。

### 滚动与动画

- 保留公共 `data-section-id`，不新增第二套全站 IntersectionObserver 导航逻辑。
- 连续滚动动画用 rAF 合帧；模块离开视口时暂停。
- sticky 长模块需要验证前后模块的进入/退出位置，尤其是模块二后接模块三、模块六后接模块七、模块十后接模块十一的边界。
- 不修改模块一、二、四、六、九、十的高度、overflow、position、动画参数或事件。

## 8. 集成验证顺序

每个模块单独执行以下流程：

1. 校验文件清单、哈希、路径、依赖和许可证。
2. 运行独立预览，检查控制台和 network 404。
3. 静态审查全局选择器、全局事件、无限动画、资源释放和绝对路径。
4. 只接入一个模块，在主站检查 360×800、768×1024、1440×900。
5. 从模块前一屏滚入、滚出到后一屏，并反向滚动。
6. 检查侧边导航、当前页码、返回顶部、开屏锁定、视频播放、场景 sticky 和小游戏指针交互。
7. 检查 reduced-motion、键盘、触屏、横竖屏切换和标签页切换。
8. 3D 模块额外检查加载失败、低网速、WebGL 不可用、context lost、离屏暂停和重复初始化/清理。
9. 对比模块一、二、四、六、九、十的基线截图或录屏，确认视觉和交互无变化。
10. 通过后才提交该模块的集成提交，再处理下一个模块。

## 9. 安全回退方案

### 前提

先修复主 Git 工作树并由用户确认一个干净的“协作开发前基线”。没有可靠基线时，不开始正式整合。

### 推荐回退层级

1. **入口级回退**：把 `main.js` renderer/import 切回旧 `CharacterSection.js`、`ActionsSection.js` 或 `EndingSection.js`，并移除对应新 CSS link/init 调用。旧文件和旧素材始终保留。
2. **提交级回退**：每个模块单独提交，可对单个集成提交做可审查的 revert；不使用 `git reset --hard`。
3. **分支级回退**：集成在专用分支完成，失败时放弃合并，不污染稳定分支。
4. **素材级回退**：新素材只在模块专属目录，移除引用即可，不影响旧素材。

任何回退前先检查工作区状态，保护用户同期优化模块一、二、四、六、九、十产生的未提交修改。不得用清理命令删除未跟踪素材。

## 10. Git 协作建议

Git 恢复后建议：

- 建立并由用户确认一个基线提交/标签。
- 主项目为三个模块分别建立集成分支，例如 `codex/integrate-module-03`、`codex/integrate-module-07`、`codex/integrate-module-11`。
- 队友若熟悉 Git，可基于同一基线分别开发并提交；若不方便共享仓库，仍按独立文件夹交付，再由主项目创建集成提交。
- 模型和大视频在采用 Git LFS 前先确认托管平台限制、配额和部署支持；不要临时把大文件塞入历史。
- 不在同一提交中混入现有模块优化和新模块集成。

## 11. 正式协作前必须解决的问题

1. 恢复或重新关联主 Git 元数据，重新获取真实 status/log/untracked 清单。
2. 用户审阅当前全部修改和素材后，明确授权建立协作前基线。
3. 确认模块七和模块十一的设计、内容、交互和验收标准。
4. 确认模块三的 3D 模型来源、授权、格式、体积、动画和交互需求。
5. 决定并固定 3D 渲染依赖及交付方式；当前主项目没有依赖管理体系。
6. 明确目标浏览器、最低设备性能、移动端策略和资源体积预算。
7. 决定大文件使用普通 Git、Git LFS 还是部署时外部托管。
8. 建立现有完成模块的截图/录屏回归基线。
9. 明确谁有权修改公共入口、全局样式和依赖配置；建议只由主项目整合者执行。

## 12. 对五个最终问题的建议答案

1. **当前是否具备多人独立开发条件？** 代码架构基本具备，但协作安全条件尚未完全具备。Git 指针必须先修复，模块七/十一需求和 3D 依赖决策也需完成。
2. **队友是否需要完整项目源代码？** 不是绝对必须。按严格模块契约可以使用最小集成包；但为了视觉衔接、响应式和滚动边界准确，建议提供一份脱敏、只读的完整源码快照，不含 `.git`、日志、输出、秘密和无关源素材。不能把当前失效 Git 元数据一起复制作为协作基线。
3. **最少需要哪些文件和信息？** `index.html`、`styles.css`、`src/main.js`、`src/data/sections.js`、`src/components/SectionShell.js`、对应旧槽位文件、前后相邻模块的 JS/CSS、`preview-server.cjs`、品牌命名规则、目标模块 ID/type、设计稿、素材、响应式/滚动/交互/验收要求，以及本规范。模块三还需模型、授权、动画列表、期望镜头和批准的 3D 依赖方案。
4. **独立文件夹还是 Git 分支？** 推荐组合使用：队友按模块独立文件夹交付，主项目在恢复基线后用独立 Git 集成分支接入。若双方能访问同一仓库并遵守基线，队友也可直接从基线开模块分支，但仍应保持模块文件夹和提交边界独立。
5. **还有哪些必须解决？** 主 Git 修复和基线确认、模块七/十一需求、3D 资产与依赖决策、浏览器/性能预算、大文件策略、版权确认、现有模块回归基线和公共文件修改权限。
